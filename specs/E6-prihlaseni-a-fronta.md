## Cíl

Nahradit tři atrapy skutečností: (1) `auth:begin` = skutečný OAuth 2.1 + PKCE S256 s loopback redirectem, token v macOS Keychain přes safeStorage, odhlášení = skutečná revokace na serveru; (2) `permission:request` = skutečné čtení macOS TCC stavu, odmítnutí se v onboardingu ukáže červeně; (3) perzistentní odchozí fronta na disku, která přežije zavření notebooku i kill -9 a nikdy nevytvoří na serveru druhý záznam téže nahrávky. Retence v Nastavení musí opravdu mazat soubory. Klíč k přepisu (B3) v aplikaci není a nemůže být — jediný povolený síťový protějšek je origin LuDone.

### 5. Desktop: úložiště tokenu — safeStorage (doporučeno), NE keytar

Nový electron/auth/store.cjs. Doporučení: **safeStorage**. Zdůvodnění: je vestavěný (nula nativních závislostí — projekt dnes nemá ŽÁDNOU, jen react/react-dom + electron/vite, a přidat nativní modul znamená rebuild matrix na každou verzi Electronu); keytar je od 2023 archivovaný a neudržovaný; @napi-rs/keyring by přinesl nativní build za nulový přínos. Na macOS safeStorage drží master klíč v login Keychainu (service `"LuDone Desktop Safe Storage"`, account `"LuDone Desktop"` — odvozeno z `app.setName()`, ověřeno v electron_browser_main_parts.cc) a náš šifrovaný blob leží na disku; ACL toho klíče je vázané na podpis aplikace, takže cizí proces ho nepřečte bez dialogu. Implementace: po `app.whenReady()` ověřit `safeStorage.isEncryptionAvailable()`; když false → token NEUKLÁDAT vůbec (přihlášení jen na běh aplikace) a říct to uživateli, nikdy nezapisovat plaintext. Blob: `path.join(app.getPath('userData'),'auth','tokens.enc')`, adresář 0o700, soubor 0o600, atomický zápis (tmp + `fsync` + `rename`). Obsah = `safeStorage.encryptString(JSON.stringify({v:1, issuer, clientId, resource, scopes, refreshToken, accessToken, accessExpiresAt, account:{email,name}}))`. Obnova: refresh 120 s před expirací (access TTL je serverově 15 min) přes `grant_type=refresh_token`. 🔴 **Jednovláknová brána (single-flight) je povinná** — server rotuje refresh token při každém použití a druhé souběžné použití spustí reuse detekci, která revokuje CELOU rodinu (grants.ts:`revokeRefreshFamily(..., reuse=true)`); tedy jeden sdílený `refreshPromise` v modulu a **nový refresh token zapsat na disk s fsync DŘÍV, než se nový access token komukoli vydá**. Odhlášení: POST `${ISSUER}/api/mcp/oauth/revoke` (client_id + token=<refresh> + token_type_hint=refresh_token) — `revokeOauthToken` najde refresh a přes `revokeRefreshFamily` zneplatní i všechny access tokeny rodiny jedním voláním; pak smazat blob, vynulovat paměť, tray na `signed-out`. Když je revoke offline: blob stejně smazat, uživateli napsat pravdu („odhlášeno lokálně, přístup odvolej v LuDone → MCP“), NIKDY netvrdit, že je odvoláno.

**Hotovo když:** Po restartu aplikace je uživatel pořád přihlášený bez prohlížeče; `security find-generic-password -s 'LuDone Desktop Safe Storage'` položku najde; `strings ~/Library/Application\ Support/LuDone\ Desktop/auth/tokens.enc | grep ldmcp_` nevrátí nic; po odhlášení vrátí uploadový endpoint na dříve zachycený access token 401 a v DB je `revoked_at` na celé rodině.

### 8. Desktop + kontrakt s E5: idempotentní resumable upload

Nový electron/queue/uploader.cjs. Kontrakt (E6 ho konzumuje, E5 implementuje — musí být dohodnutý PŘED rozdělením worktrees): (a) `POST /api/desktop/recordings` s hlavičkou `Idempotency-Key: <recordingId>` a tělem `{recordingId, startedAt, durationMs, tracks:[{source,bytes,sha256}]}` → 200 `{serverRecordingId, uploadedBytes:{microphone,system}, state}`. 🔴 Idempotenci NESMÍ garantovat slušné chování klienta, ale **unikátní index `(user_id, client_recording_id)`** na serveru + `ON CONFLICT DO NOTHING RETURNING` — opakované volání vrací TÝŽ záznam, nikdy druhý řádek. (b) `PUT /api/desktop/recordings/{serverRecordingId}/tracks/{source}` s `Content-Range: bytes A-B/total`; server připojí bajty JEN když `A === aktuální uložená velikost`, jinak 409 s `{uploadedBytes}` a klient se přesune na ten offset (409 se nepočítá jako pokus). (c) `POST .../complete` s per-stopa sha256 → server přepočte hash uloženého souboru; neshoda = 422 a klient tu stopu pošle znovu od nuly (max 3×, pak `failed`). Complete je idempotentní. (d) Po restartu i po probuzení se offset bere VŽDY ze serveru (odpověď (a)), nikdy z lokálního manifestu. Backoff: `min(30s × 2^(attempts-1), 6h)` s ±20 % jitterem, `nextAttemptAt` v manifestu. Retryovatelné: síť, 5xx, 429 (respektovat `Retry-After`), 408. Neretryovatelné → `failed`: 400, 413, 3× 422. 🔴 401 → jeden pokus o refresh; když refresh vrátí `invalid_grant` (odvolaný consent), fronta se PAUZUJE ve stavu `queued`, pokusy se NEZAPOČÍTAVAJÍ a aplikace jde do `signed-out` — jinak odvolání consentu tiše vyčerpá retry budget a nahrávky skončí jako `failed`. Pumpa: jeden worker, max 1 souběžný upload; budí ji `app.whenReady`, `powerMonitor` události `resume`/`unlock-screen`, `net.isOnline()` přechod, timer na nejbližší `nextAttemptAt` a tlačítko „Zkusit teď“. `powerMonitor.on('suspend')` a `app.on('before-quit')` → `AbortController.abort()` a uložit stav.

**Hotovo když:** Vypnutí Wi-Fi v půlce uploadu, zapnutí za 2 min → dojede sám; server má jeden záznam; `sha256` uloženého souboru == lokální; ruční zopakování celého POST /recordings curlem s týmž recordingId vrátí týž serverRecordingId a v DB nepřibude řádek.

## Pasti — co tuhle etapu shodí

- 🔴 Rotace refresh tokenu + dva souběžné uploady = server vyhodnotí reuse a revokuje CELOU rodinu tokenů (grants.ts `revokeRefreshFamily(..., reuse=true)`) → uživatel je bez varování odhlášený. Povinný jediný sdílený refreshPromise (single-flight) a nový refresh token zapsat na disk s fsync DŘÍV, než se nový access token komukoli vydá.
- 🔴 safeStorage odvozuje název položky v Keychainu z názvu aplikace (`"LuDone Desktop Safe Storage"`, ověřeno v electron_browser_main_parts.cc). Ad-hoc podpis mění cdhash při každém buildu → macOS považuje každý build za jinou aplikaci → opakované dialogy Keychainu, případně nedešifrovatelný blob. E6 tedy stojí na stabilní podpisové identitě z nálezu C1 (vlastní certifikát drží „designated requirement“). A pozdější přejmenování aplikace osiří všechny uložené tokeny.
- 🔴 `systemPreferences.askForMediaAccess('screen')` NEEXISTUJE — Electron umí u obrazovky jen číst stav. Kdo to přehlédne, napíše druhou atrapu. Dialog vyvolá až skutečný pokus o zachycení (`desktopCapturer.getSources`).
- 🔴 Jednou odmítnutý mikrofon už dialog nikdy nevyvolá a po povolení v Nastavení systému je podle dokumentace nutný RESTART aplikace. Onboarding, který jen znovu čte stav, bude vypadat rozbitě — musí nabídnout `app.relaunch()`.
- 🔴 Cookie `mcp_oauth_initiator` je `Secure` → celý consent flow tiše selže (initiator_mismatch) proti serveru na prostém http. Testovat výhradně proti labs přes https, ne proti localhost:3000.
- 🔴 `resource` je dnes natvrdo `${origin}/api/mcp` na třech místech a `validateOauthAccessTokenRecord` natvrdo vyžaduje `mcp:read`. Nejjednodušší „oprava“ — dát desktopu `mcp:read` — by z diktafonu udělala klienta s přístupem k CELÉMU katalogu MCP nástrojů (peníze, rozpočty, faktury). Least privilege: desktop dostane výhradně `desktop:upload` na resource `/api/desktop`.
- 🔴 Loopback server naslouchající na `0.0.0.0`/`::` nebo přijímající libovolnou hlavičku Host je otevřená brána pro DNS rebinding — cizí web si odnese authorization code. Vázat výhradně na `127.0.0.1`, ověřovat Host přesně a přijmout jen první callback.
- 🔴 Připojování bajtů bez serverové kontroly offsetu (Content-Range vs. uložená velikost) způsobí, že opakovaný pokus soubor prodlouží a upload přesto „uspěje“. Ochranou není chování klienta, ale unikátní index `(user_id, client_recording_id)` a kontrola offsetu na serveru.
- 🔴 401 z odvolaného consentu se nesmí počítat jako běžné selhání uploadu — jinak retry budget dojde a nahrávky skončí ve stavu `failed`, přestože stačilo se znovu přihlásit. 401 → jeden refresh; `invalid_grant` → pauza fronty a `signed-out`, bez započtení pokusu.
- 🔴 Retence, která maže dřív, než server potvrdí `complete`, je ztráta dat. Mazat výhradně stav `uploaded`.
- 🔴 Nastavení retence v localStorage je nefunkční z podstaty — mazající strana (main proces) do localStorage rendereru nevidí a cache se čistí. Musí do souboru v userData přes IPC.
- 🔴 Manifest musí být na disku PŘED prvním bajtem zvuku. `finalizeRecordingSessionsForOwner()` zachraňuje nahrávku i po pádu rendereru; bez manifestu je ta nahrávka pro frontu neviditelná.
- ⚠️ Vadná hlavička Opus ve WebM (nález B6) se NEOPRAVUJE v desktopu remuxem — porušilo by to kontrakt sha256 (hashuje se přesně to, co se nahraje). Řeší server (E5).
- ⚠️ Info.plist dnes nemá `NSAudioCaptureUsageDescription`, který macOS 14.2+ vyžaduje pro zachycení zvuku přes desktopCapturer. Balení bez něj může zachycení systémového zvuku na novějším macOS shodit — přesně tu funkci, kvůli které projekt vznikl.
- ⚠️ `shell.openExternal` s nevalidovanou URL je spouštěč cizího kódu. Vždy přes wrapper kontrolující origin a https.
