## Tělo zadání

### Důvěryhodný target a auth kontext

Přidej do serializovaného queue store trusted getter detailu podle bezpečného row ID a aktuální revize T-03. Getter znovu stabilně přečte současný primární manifest a vrátí pouze do main procesu `ownerFingerprint` a pro každou relevantní stopu `{ recordingId, declaredBytes, sha256 }`. Stará revize, neplatný manifest, cizí vlastník, symlink nebo cesta mimo `recordingsDirectory` se odmítnou. Cestu, fingerprint, token ani syrový manifest nikdy neposílej do rendereru.

Podle D14 je primární manifest autoritou identity a bezpečných cest. Pro skutečné upload hash/bytes lze použít `item.manifestPath` pouze tehdy, když jde o primární manifest samotný nebo přesně jeho již existující `${primary}.recovered-upload-v1.json` se shodným `sourceManifestPath`. U známého sidecaru vyžaduj shodné UUID, `createdAt`, zdroje a názvy souborů; známé nenulové velikosti a hashe primárního manifestu se musejí shodovat. Oba soubory čti omezeně, stabilně a bez následování symlinků, s využitím bezpečného T-03 snapshotu a jeho canonical root. Odmítni libovolný jiný sidecar, výměnu nebo neshodu. Getter nic negeneruje, neobnovuje ani nepřepisuje a nepotřebuje dosud existující audio po retenci.

Verifier má rozhraní `createRecordingVerifier({ fetchImpl, getContext, isContextCurrent, now })` s metodami `verify(trustedTarget)` a `invalidate()`. `getContext` smí vzniknout jen z platné `readUsableAuthSession` se správným issuerem, API resource, scope `nahravky:upload`, aktuálním ownerem a auth generation. Nevolej `resolveUploadCompanyId` ani žádný GET firmy. Před cache a GET ověř owner shodu i platnost kontextu; po každém `await` znovu ověř `isContextCurrent`. Výsledek rozběhnutý pod starým účtem, originem nebo generation zahoď.

Změna identity, originu nebo nový login invalidují cache. Logout zavolá invalidaci synchronně a nesmí čekat na dokončení rozběhnutého GET.

### HTTP klient a serverové výsledky

Ještě před exportem zpevni stávající `createRequester`: odmítni absolutní a scheme-relative URL, credentials, search, hash a pathname, který po rozlišení uniká mimo zvolený origin. Vlastní headers nesmí přepsat `Authorization` ani `Cookie`. Zachovej stávající timeout, chybový model, Bearer hlavičku, `redirect: "error"` a parser `Retry-After`; nevytvářej nový klient.

Při ručním ověření udělej jeden GET pro každou známou relevantní stopu, nejvýše dva a sekvenčně. Chybějící `recordingId` znamená `not_verified` a nula requestů pro tuto stopu; nepoužívej INIT k dohledání ID. Jednostopá nahrávka dělá nejvýše jeden GET a legacy položka bez ID žádný.

Stav `complete` přiznej stopě jen pro serverový stav `stored` nebo `normalized`, `missing: []`, kladné safe-integer `declaredBytes` a lowercase/uppercase tolerovaný hex64 `sha256`, které přesně odpovídají aktuálnímu lokálnímu manifestu. `uploading` mapuj na `incomplete`, `failed` na `server_failed`. Rozdíl vrať jako konkrétní bezpečný kód pole bez syrové serverové či lokální hodnoty; vadná 200 odpověď je `invalid_response`. HTTP 404 znamená pouze `not_found_for_account`, ne tvrzení, že záznam nikde neexistuje. Lokální dostupnost audia se tím nemění.

### Cache, rozpočet a 429

Paměťová cache má TTL 60 sekund a klíč zahrnuje generation, issuer, owner, row ID, track, `recordingId`, hash a bytes. Souběžná stejná ověření deduplikuj. Před prvním `await` atomicky rezervuj celý počet studených requestů daného ověření; pokud se nevejde celý, neposílej žádný.

Sliding limit procesu je 30 GET za posledních 60 minut, tedy nejvýše 15 studených ověření dvoustopých nahrávek. Po restartu se resetuje a nevytváří historii. Serverový limit 120 GET/h/user je sdílený s webem i GET požadavky upload klienta, takže lokální strop není příslib dostupné serverové kvóty.

Po 429 použij serverový `retryAt`, při chybějícím nebo vadném údaji jednu hodinu od `now`; druhou stopu neposílej a nic automaticky neopakuj. Blokaci drž podle issueru a vlastníka odděleně od cache výsledků: logout, nový login ani invalidace cache nesmějí v témže procesu zrušit dosud platné `Retry-After` téhož vlastníka.

### IPC, otevření webu a UI

Verify i open-web kanál zapoj přes existující sender guard jen pro okno Nastavení. Renderer předá pouze row ID, revizi a označení stopy; main znovu získá trusted target a platný aktuální kontext. URL sestaví výhradně main jako `/nahravky/<recordingId UUID>` na právě platném povoleném web originu a teprve potom ji předá `shell.openExternal`. Renderer nesmí dodat URL, origin ani `recordingId`; cizí, stará nebo bez-ID stopa se neotevře.

Do hotového dashboardu T-03 přidej pouze ruční tlačítko „Ověřit v LuDone“, dva oddělené per-track výsledky a čas ověření. Odliš prázdný/chybový lokální přehled od chyby serverového ověření. Při renderu, otevření Nastavení ani ručním „Obnovit přehled“ nevolej server.

## Akceptace

- Mock test prokazuje přesný GET, Bearer a `redirect: "error"`; špatný owner, token, scope, resource nebo current guard způsobí nula fetchů.
- Dual, single a legacy bez ID mají přesně 2, 1 a 0 GET. Druhá stopa se po 429 nepošle.
- `stored`/`normalized`, uploading, failed, 404, hash/bytes/missing mismatch a vadná 200 odpověď mají odlišné bezpečné výsledky.
- TTL, explicitní invalidace a změna účtu během pending requestu nepustí starý výsledek do UI. Souběh respektuje deduplikaci a atomický limit 30 GET/60 min.
- Neplatná URL nebo hlavička je odmítnutá před fetch; stávající timeout, HTTP error a `Retry-After` regresní testy zůstávají zelené.
- End-to-end test projde trusted store detail → chráněný IPC → preload → ruční klik → oba výsledky a čas v rendereru. Foreign frame, vadný payload, stale revize a open-web cizí položky jsou odmítnuté.
- Regrese skutečné recovery cesty projde primární neúplný manifest → existující efektivní upload manifest → uložená serverová ID → trusted getter → mock GET, také po retenci audia. Vadný nebo podvržený sidecar nevyvolá fetch.
- Žádný produkční request, `ui-smoke` ani `audio-smoke`; server a skutečný login tímto packetem nejsou ověřené.

1. Po obnovení obou ochran musí legitimní dual a single ověření zůstat zelené s přesným počtem GET a bezpečnými výsledky.
2. Invalid owner/scope/resource/token, limit 30/h, 429 skip druhé stopy a foreign-frame/payload guard musí dál skončit bez nepovoleného fetch nebo otevření URL.
